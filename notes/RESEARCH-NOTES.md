## Lens: first-run-adoption (recovered from failed run)

### First-boot admin password is unrecoverable, and the deploy docs contradict the code
- **severity** critical · **effort** M · **category** first-run-blocker
- **evidence** UnisubmitApplication.java:67-103; EmailService.java:44,52; AuthController.java:69-91; deploy/README.md:52-54; deploy/RAILWAY.md:17-28; deploy/unisubmit.env.example (no ADMIN_INITIAL_PASSWORD)
- **detail** On a fresh non-demo database `bootstrapAccounts` creates exactly ONE account (`admin`) whose password is either `ADMIN_INITIAL_PASSWORD` or a generated 20-char string logged ONCE at WARN (UnisubmitApplication.java:83-102). Three things then combine into a hard lockout:

1. The docs the operator actually reads are wrong or silent. `deploy/README.md:52-54` still says "The app auto-creates admin / lecturer / student (all password123) on first boot" — untrue since the demo gate landed (application.yml:111-114 defaults `SEED_DEMO_ACCOUNTS=false`). `deploy/RAILWAY.md:17-28` lists the required variables and does not mention `ADMIN_INITIAL_PASSWORD`. `deploy/unisubmit.env.example` — the file the server operator fills in — omits it entirely. Only `.env.example:23` (local dev) documents it.
2. There is no recovery. `AuthController.requestPasswordReset:78` routes any non-STUDENT to `passwordResetService.requestCode`, and `EmailService.sendPasswordResetCode` does `String to = user.getUsername()` (EmailService.java:44,52). The bootstrap admin's username is the literal string `admin`, not an email — the send fails, asynchronously, into a log. The UI still redirects to `/reset-password?sent`, telling the admin a code was emailed. The fallback branch (AuthController.java:83-89) only raises an in-app notification to ROLE_ADMIN users: "Reset it from Admin › Accounts" — circular when the admin is the locked-out party.
3. `ADMIN_INITIAL_PASSWORD` is ignored once an admin row exists (UnisubmitApplication.java:79-81), so setting it after the fact and redeploying does nothing.

An IT admin who deploys on Railway, closes the log tab, and comes back tomorrow has no path into their own installation short of manual SQL or wiping the database.
- **do** Take an operator-supplied email as the bootstrap admin's username (or store an email on the account) so the existing emailed-code reset actually works for them. Fail fast at boot with a clear message if a fresh DB has neither `ADMIN_INITIAL_PASSWORD` nor an existing admin, rather than generating a password nobody will read. Also write the generated password to a file under the upload dir, not only to stdout. Then fix `deploy/README.md:52-54`, add the variable to `deploy/RAILWAY.md` and `deploy/unisubmit.env.example`.
- **why** This is the very first interaction a school has with the product, and its failure mode is total and silent. Every other item in this audit is downstream of being able to log in at all.

### No guided setup exists — the admin lands on a dashboard of zeros with no next step
- **severity** critical · **effort** S · **category** onboarding
- **evidence** AdminDashboardController.java:45-70; admin/dashboard.html:21-52,66-91,152-203; admin/layout.html:36-94; grep setup|onboard|wizard across src/ finds no such controller/template; ROADMAP.md has no matching item
- **detail** There is no setup wizard, checklist, or first-run state anywhere: grepping `src/` for setup|onboard|wizard|getting.started|first.run|checklist returns only unrelated BrandingService and test hits. No controller or template covers it.

What the admin actually sees after logging in: `AdminDashboardController.dashboard` puts 6 population counters and 8 submission-status counters on the model, and `admin/dashboard.html` renders them as a stat strip of zeros (lines 21-52), a rail of zeros (96-119), and a Chart.js doughnut fed eight zeros (152-203) which draws an empty ring with no empty-state copy. The only forward guidance is a "Quick actions" grid (66-91) listing six destinations — faculties, departments, programmes, units, accounts, landscape — in no stated order, omitting Branding, Curricula, Lecturer mappings and Bulk import entirely, and including Research Landscape, which is meaningless until submissions exist.

The sidebar (admin/layout.html:36-94) groups 12 destinations under Overview / Academic structure / People / Intelligence. The grouping is sensible but conveys no sequence and no state — Curricula looks exactly as available on minute zero as it does after the tree is built, even though it cannot be used until programmes and units exist.

ROADMAP.md contains no onboarding or first-run item at all (grep for onboard|first-run|setup wizard|guided|adoption returns only demo-seeder lines 337-338 and 548). This is a blind spot, not deferred work.
- **do** Add a first-run checklist card to the dashboard driven entirely by counters already on the model — no new queries. Nine rows: Branding → Faculties → Departments → Lecturers → Programmes → Units → Curricula → Students → Enrolments/Teaching assignments, each linking to its screen, each ticking off when its counter goes non-zero, and each greyed with a "needs X first" note while its prerequisite is zero. Hide the card once all are satisfied. Replace the all-zero doughnut with an empty state pointing at the same checklist.
- **why** The admin knows their institution but not this app's data model. Nothing tells them that Faculty must precede Department must precede Programme, or that Curriculum is the join that makes submission possible. They will click around, create things in the wrong order, hit errors, and conclude the product is broken.

### The required import order is only half-documented, and the import page's own layout contradicts it
- **severity** high · **effort** S · **category** onboarding
- **evidence** admin/import.html:161,183,205,208-212,174-175,196-197; AcademicImportService.java:79-94,271-282; CsvImportService.java:164-167,435-438
- **detail** `admin/import.html` renders three blocks in DOM order: Students (161-180), Lecturers (183-202), Academic structure (205-231). That order is wrong.

Students carry `programmeCode`, validated against existing programmes (CsvImportService.java:164-167 → "Unknown programme code"). Lecturers carry `departmentCode`, validated against existing departments (CsvImportService.java:435-438). Both of those parents live in the Academic structure block *below* them on the page. In the other direction, `TEACHING_ASSIGNMENT` requires a `staffid` that resolves to a LecturerProfile and `ENROLLMENT` requires an `admissionnumber` that resolves to a StudentProfile (AcademicImportService.java:271-282) — so accounts must be created *before* those two.

The genuine order is interleaved and is written down nowhere: Faculties → Departments → **Lecturers** → Programmes → Units → Curriculum → **Students** → Teaching assignments → Enrolments.

What the UI offers instead: one sentence, "Import them in this order — each level references the one above it by code" (import.html:208-212), scoped only to the academic block, above seven visually identical unnumbered cards whose sequence is implied purely by the declaration order of the `Kind` enum (AcademicImportService.java:79-94). Nothing on the Students or Lecturers cards says what must exist first; their hints only say to use "YOUR programme codes (see Admin → Programmes)" (import.html:174-175) and "YOUR department codes" (196-197), which presumes those pages are already populated.
- **do** Number all nine uploads 1–9 in one continuous list, move the Students card between Curriculum and Teaching assignments and the Lecturers card between Departments and Programmes so DOM order equals required order, and label each card "Step N of 9 — requires: <parent kind>". Disable a card with an inline reason when its prerequisite count is still zero.
- **why** An admin working top-to-bottom down the page — the natural reading order — starts with the two imports that cannot possibly succeed yet. Their first two attempts fail with 100% invalid rows before they ever reach the block that explains ordering.

### Nine separate upload cycles, no progress memory, and the page wipes itself after every step
- **severity** high · **effort** M · **category** onboarding
- **evidence** AdminImportController.java:58-99,137-194; admin/import.html:161,183,205; admin/curricula.html:20-44; admin/assignments.html:20-51
- **detail** Making the app usable requires nine distinct bulk uploads (students, lecturers, and seven academic kinds), each a three-page-load loop: choose file → POST `.../preview` (re-renders `admin/import`) → POST `.../apply` → `redirect:/admin/import` (AdminImportController.java:58-99,137-194). That is ~27 page transitions, 9 template downloads, and 9 hand-authored spreadsheets — plus branding, which is a separate screen.

Worse, the page has no memory. All three upload blocks are wrapped in `th:if="${creds == null and preview == null and lecturerCreds == null and lecturerPreview == null and academicPreview == null}"` (import.html:161,183,205), so the instant any preview exists every other card vanishes — mid-flow you cannot see which steps remain. After apply you are redirected back to a flat list of nine identical cards with nothing marking what is already done. On step 7 of 9 the screen is indistinguishable from step 1.

The manual alternative is worse, not better: seven CRUD screens behind modals, where each curriculum row needs programme + unit + year + semester (admin/curricula.html:20-44) and each teaching assignment needs lecturer + curriculum + year + semester (admin/assignments.html:20-51). For a small faculty that is hundreds of modal submissions.
- **do** Two changes, both cheap. (a) Keep all nine cards rendered at all times with a per-kind status tick sourced from the counts the dashboard already queries, and show the preview inline under its own card instead of replacing the page. (b) Accept a single multi-sheet .xlsx whose sheet names map to `Kind` — `AcademicImportService.parseWorkbook` already opens a workbook and reads `wb.getSheetAt(0)` (line 215), so iterating sheets in enum order collapses nine uploads into one and makes the ordering problem disappear by construction.
- **why** Nine uploads with no progress indicator is where a busy IT admin abandons a pilot. The work is not intrinsically hard — the schema is small — but the interaction cost and the constant loss of place make it feel like it is.

### AcademicImportService.apply wraps the whole batch in one transaction while its javadoc and its UI both promise per-row safety
- **severity** high · **effort** S · **category** correctness
- **evidence** AcademicImportService.java:302-334 (@Transactional at 307, per-row catch at 325-329); AdminImportController.java:181-192; CsvImportService.java:42-43 (no @Transactional)
- **detail** `apply` is annotated `@Transactional` at the method level, covering the entire row loop (AcademicImportService.java:307-334). Its javadoc immediately above (302-306) states the opposite: "Applies row by row in its own transaction boundary per row via the repository calls — one bad row is reported and skipped rather than rolling back the batch, matching how the student importer behaves."

The per-row `catch (Exception ex)` at 325-329 increments `failed` and continues, but a persistence exception — a constraint violation, a flush failure — marks the surrounding transaction rollback-only. Commit then throws and *every* row created in that batch is discarded. Meanwhile `AdminImportController.applyAcademic` has already composed and flashed "N created, M already existed, 1 failed" from the returned `ApplyResult` (lines 181-192).

The comparison to the student importer is also wrong in the other direction: `CsvImportService` carries no `@Transactional` anywhere (class declared at line 42-43), so `applyStudents` genuinely is partial-safe per row via `userService.createStudent`'s own transaction. The two importers behave differently and the documentation asserts they behave the same.
- **do** Remove `@Transactional` from `apply` and put `@Transactional(propagation = REQUIRES_NEW)` on each applier, or wrap each row in a `TransactionTemplate` — the pattern `AIInsightProcessingService` already uses for exactly this reason. Then correct the javadoc. Add a test that asserts good rows survive a bad row in the same batch.
- **why** At adoption scale this is silent data loss with a success message on top: a 3,000-row enrolment import where one row trips a unique constraint reports "2,999 created" and persists nothing. The admin moves on believing the step is done, and the failure only surfaces weeks later when students cannot see their units.

### Wrong-order imports fail safely but never name the fix, and enrolment/assignment imports silently invent curriculum rows
- **severity** medium · **effort** S · **category** error-handling
- **evidence** AcademicImportService.java:258-285,288-298,376-393,396,411; admin/import.html:258-268,272; AdminImportController.java:152-160
- **detail** The good news first: ordering violations are caught before any write. `validate` pre-checks every parent reference (AcademicImportService.java:258-285) — programmes imported before departments produce `"Unknown department code 'CS'"` on every row, `validCount` is 0, and `admin/import.html:272` therefore never renders the Import button, only "Back". Nothing is written and the session stash is cleared on fatal previews (AdminImportController.java:152-160). That is well built.

Two gaps remain. First, the message stops at "Unknown department code 'CS'" and never says "import Departments first" — the admin is told what is missing but not that they are simply at the wrong step. And every failing row gets its own table row (import.html:258-268), so a 5,000-row file renders 5,000 identical red badges with no summary.

Second, and less visible: `applyCurriculum` is find-**or-create** (AcademicImportService.java:376-393), and both `applyTeachingAssignment` (396) and `applyEnrollment` (411) call it. Importing Enrolments before Curriculum therefore does not fail — it *fabricates* curriculum rows from the enrolment file's programme/unit/year/semester columns. No error, no warning, no mention in the preview. The Curricula screen later shows rows the admin never authored and cannot account for.
- **do** When every invalid row shares one parent-kind error, replace the row table with a single banner: "None of these rows can be imported yet — import Departments first" plus a direct link. Collapse repeated identical errors into a count. For the auto-create: either surface it in the preview ("this will also create 42 curriculum rows") or refuse it and require Curriculum to be imported first, consistent with every other kind.
- **why** The first failure is a wasted round trip that reads as a product defect rather than a sequencing mistake. The second is worse — it quietly diverges the admin's mental model of the curriculum from what is in the database, in exactly the table that governs which students can submit against which units.

### No in-app sample data, and the env-var path needs three flags plus a production security regression
- **severity** medium · **effort** M · **category** onboarding
- **evidence** CollaborationDemoSeeder.java:33-41,134-141,180,195,211; RichTestDataSeeder.java:22-24,87-114,117-140,143-180; application.yml:111-114,120-129; README.md:107-118 (documents the local profile only)
- **detail** There is no way to populate a demo from inside the app. Both seeders are `@ConditionalOnProperty`: `CollaborationDemoSeeder` on `unisubmit.demo.seed-collaboration` (line 39-40, @Order(10)) and `RichTestDataSeeder` on `unisubmit.demo.seed-rich-test-data` (line 22-24, @Order(15)), both defaulting false in production (application.yml:126,129). Changing either requires an environment variable and a restart.

They are also chained in a way no document records. `RichTestDataSeeder.seedRichTestData` aborts unless users `student` and `lecturer` exist (lines 109-114) and again unless the `DEMO-BCS`/`DCS410` curriculum created by `CollaborationDemoSeeder` exists (117-140, which logs "Seeding aborted" and returns). So `DEMO_SEED_RICH=true` on its own does nothing at all. It further mutates the seeded `S001`/`L001` profiles directly (143-180).

A populated evaluator demo therefore requires all three of `SEED_DEMO_ACCOUNTS=true`, `DEMO_SEED_COLLABORATION=true`, `DEMO_SEED_RICH=true` — and the first is the flag application.yml:111-114 explicitly warns against: "Enabling this in production recreates the old hole: a live admin login with a password that is in the source." So the only way to show a populated app is to reintroduce `admin`/`password123`.
- **do** Add an admin-only "Load sample data" action (and a matching "Remove sample data") that runs the seeders against synthetic accounts with generated passwords rather than the `password123` trio, decoupling demo content from `SEED_DEMO_ACCOUNTS`. Both seeders are already marker-guarded (CollaborationDemoSeeder:134-141, RichTestDataSeeder:89-95), so idempotence is solved. Until then, document the three-flag combination and its dependency order in deploy/RAILWAY.md.
- **why** An evaluator, a pilot department head, or the admin themselves cannot see what the product looks like when it is working. They see zeros and have to build a whole academic tree on faith before the first screen becomes meaningful — and the documented shortcut costs them a known-password admin account.

### Public self-registration is live from minute zero, yet impossible to complete until the tree exists — with no message either way
- **severity** medium · **effort** S · **category** first-run-blocker
- **evidence** SecurityConfig.java:44,50; register.html:47-66; AuthController.java:143-174 (params at 148-150, createStudent at 169)
- **detail** `SecurityConfig` permits `/register` anonymously (line 44) and `/api/academic/**` anonymously (line 50). Registration is therefore open to the internet from the moment the container starts, before the admin has configured anything: no invite, no email verification, no allowlist of valid admission numbers.

At the same time it cannot actually be used. `register.html` marks faculty, department and programme `required` (lines 47-66) and fills them by cascading fetches to `/api/academic/departments` and `/api/academic/programmes`. On a fresh deploy the faculty list is empty, so the first dropdown has nothing to select and the form cannot be submitted — with no explanation rendered. A student who finds the URL on day one sees three dead dropdowns.

The two facts do not cancel out, because the client-side `required` is the only gate: `AuthController.register` declares `courseId`, `departmentId` and `facultyId` as `required = false` (lines 148-150) and calls `createStudent(..., courseId, 1, 1)` at line 169. A direct POST creates a STUDENT with no programme.
- **do** Gate `/register` behind an admin toggle that stays off until at least one programme exists, and validate the submitted admission number against imported StudentProfiles so self-registration claims a pre-loaded roster row instead of minting arbitrary accounts. In the meantime, render "Registration isn't open yet — contact your department" when the faculty list comes back empty, and enforce the programme requirement server-side.
- **why** Two adoption problems in one endpoint: the school's deployment is publicly writable before the admin has done anything, and the legitimate first student is blocked by an unexplained empty form. Both land in the same week of a pilot.

### Bulk-imported students get a null semester, and a blank programme column silently creates a mis-attached cohort
- **severity** medium · **effort** S · **category** data-quality
- **evidence** CsvImportService.java:164-167,277-278,489; UserService.java:167-172; SubmissionService.java:93-110,130; StudentController.java:96-102; AuthController.java:169
- **detail** Two defaults in the student importer quietly degrade every account it creates.

Semester: the template is `name,phone,studentId,programmeCode,year` (CsvImportService.java:489) — there is no semester column — and `applyStudents` calls `createStudent(r.studentId(), r.phone(), password, r.name(), r.programmeId(), r.year(), null)` (lines 277-278), so `StudentProfile.currentSemester` is set to null (UserService.java:170-171). Submission still works, because curriculum resolution keys on programme alone (SubmissionService.java:93-99) and the unit dropdown is department-scoped (StudentController.java:96-102) — but CLASS_REP authority is scoped to programme+year+semester, and every semester-scoped view sees null for the entire imported population. Note the contrast: self-registration hardcodes year 1, semester 1 (AuthController.java:169), so the two entry paths produce differently shaped profiles.

Programme: `programmeCode` is optional — validated only when non-blank (CsvImportService.java:164-167). A school that omits the column imports cleanly and gets a whole cohort with no programme, which then falls into the lenient path in `SubmissionService:100-110`: "use the first curriculum for this unit". Every project from that cohort attaches to whatever curriculum happens to sort first, recorded only as an audit-log aside, "(no programme on file — first curriculum used)" (line 130).
- **do** Add `semester` to the student template and pass it through `applyStudents`. Keep `programmeCode` optional but make the preview warn on it: "N students have no programme — they will be able to submit, but their work will attach to an arbitrary curriculum." Reconcile the self-registration defaults (year 1 / semester 1) with the importer so both paths produce the same profile shape.
- **why** Both defects are invisible at import time — the preview shows green OK badges — and surface weeks later as submissions filed against the wrong curriculum and class reps whose scope does not match anyone. Re-importing does not fix them, because admission numbers already exist.

### Branding — the admin's step zero — cannot be saved if the in-page theme engine fails
- **severity** low · **effort** S · **category** robustness
- **evidence** AdminBrandingController.java:37-40,60-62,65-71; admin/branding.html:756-761; static/js/vendor/theme-engine.iife.js
- **detail** `AdminBrandingController.saveBranding` rejects an empty `tokensJson` with "No theme was generated in the browser — reload the page and try again" (lines 65-71), and the page refuses to post without generated tokens, showing "No theme generated yet — adjust a color or upload a logo first" (admin/branding.html:756-761). The entire palette is computed client-side by `static/js/vendor/theme-engine.iife.js`.

The engine is self-hosted so there is no CDN dependency, and the error message is honest rather than the opaque Jackson end-of-input it replaced. But the server already receives `basePrimary`, `baseSecondary` and `baseNeutral` as separate parameters (lines 60-62, defaulted for the pickers at 37-40) and does nothing with them when tokens are missing. The failure mode is a reload loop with no fallback, on the screen that is step one of adoption and the one most likely to be attempted on a low-end phone or a locked-down campus browser.
- **do** When `tokensJson` is absent, derive a minimal token block server-side from the three base colours already posted, save it, and flash "Saved with a basic palette — reopen Branding on a desktop browser for the full theme." Keep the current message only when the base colours are missing too.
- **why** Branding is the first thing an adopting school does and the change that makes the deployment feel like theirs. A dead end here — on any device where the engine does not run — reads as the product being broken before any real data has been entered.


## Lens: competitive-edtech + cross-industry-ux

### Deadlines are announcements, not a coursework object — no due/cut-off split, no penalty maths, no per-student extension
- **severity** critical · **effort** L · **category** deadlines-and-late-policy
- **evidence** https://docs.moodle.org/29/en/Assignment_settings ; https://www.monash.edu/learning-teaching/teachhq/moodle/assignment/how-to/extensions-and-resubmissions ; https://www.kenyon.edu/offices-and-services/center-for-innovative-pedagogy/instructional-technology/moodle/moodle-assignments-due-dates-and-cutoff-dates/ ; https://city-uk-ett.libguides.com/staff/moodle/extensions-resubmissions/Moodle-Assignment
- **detail** UniSubmit has no Assignment entity. A deadline exists only as `Announcement.deadline` plus a `lateWindowOpen` boolean (A:/unisubmit-main/unisubmit-main/src/main/java/com/unisubmit/domain/Announcement.java:38-42, toggled via LecturerController.toggleLateWindow at line 222), or loosely as `Unit.submissionDeadline` (AdminUnitController.java:57-64). `SubmissionVersion.late` is a bare boolean with no minutes-late value. The actual penalty rule is prose typed into an announcement message — literally '10% penalty' as free text in RichTestDataSeeder.java:264. Nothing computes it, nothing enforces it, and there is no way to give one student an extension without opening the late window for the entire class.

Every mature platform separates two distinct instants. Moodle's due date is when penalties begin but submission is still possible; the cut-off date is when the submit button disappears entirely; and extensions are granted per student via overrides, individually or by ticking a set of students in the grading table. Canvas does the same through differentiated 'assign to' dates. The two-date model is what makes 'late' a computable quantity instead of a flag.
- **do** Add an `Assignment` entity in com.unisubmit.domain keyed to `Curriculum` (which already carries programme+unit+year+semester): title, instructions, openAt, dueAt, cutoffAt, latePolicy enum (NONE | FLAT | PER_DAY), penaltyPercent, penaltyCapPercent, maxAttempts, and a rubric FK (see finding 2). Add `Submission.assignment` (nullable, so existing free-standing project submissions keep working) next to the existing `curriculum` FK in Submission.java. Add `AssignmentExtension` (assignment, student, newDueAt, newCutoffAt, reason, grantedBy, grantedAt) so a lecturer overrides one student without touching the class. Replace the `lateWindowOpen` boolean and the toggle-late-window endpoint entirely — cutoffAt subsumes it; keep Announcement for actual announcements. Change `SubmissionVersion.late` to `minutesLate` (Integer, null = on time) and store rawScore / penaltyApplied / finalScore on the grade record so the arithmetic is auditable rather than mental. Because CLASS_REP is already a scoped authority, let a class rep *request* a class-wide extension that the lecturer approves in one click — that maps directly onto how Kenyan cohorts actually negotiate deadlines.
- **why** Without a due/cut-off split the lecturer's only lever is a class-wide on/off switch, so one student's hospital admission forces the deadline open for 300 people. Late penalties applied by hand in a spreadsheet are the single largest source of grade disputes, and an uncomputed penalty is an unappealable one.

### Grading is one free-text blob plus a 0–100 integer — no rubric, so marks are neither consistent nor explainable
- **severity** high · **effort** L · **category** grading-workflow
- **evidence** https://guides.gradescope.com/hc/en-us/articles/22249389005709-Grading-submissions-with-rubrics ; https://people.eecs.berkeley.edu/~pabbeel/papers/2017-LaS-gradescope.pdf ; https://www.elearning.fse.manchester.ac.uk/getting-started-with-canvas/canvas-essentials-rubrics/ ; https://support.google.com/edu/classroom/answer/9093530
- **detail** `Feedback` (A:/unisubmit-main/unisubmit-main/src/main/java/com/unisubmit/domain/Feedback.java) is a TEXT message, a lecturer FK, and `Integer grade` (0–100, nullable). The lecturer UI in A:/unisubmit-main/unisubmit-main/src/main/resources/templates/lecturer/review-split.html:135-149 is a textarea and a number input. That is the entire grading model. The student is told '68' and a paragraph, and has no way to see where the other 32 marks went.

Gradescope's core insight is that a rubric is not a form you fill in before grading — it is a structure you *build while grading*: the rubric starts with one item, a grader adds an item when they meet a new mistake, and changing an item's point value retroactively rescores every submission already graded. Canvas surfaces the rubric to students before they submit, which converts it from a marking tool into an expectations tool. Google Classroom pitches rubrics primarily as transparency: students know what is required before submitting.
- **do** Add `Rubric` (owned by Assignment), `RubricCriterion` (label, description, maxPoints, ordinal), and optionally `RubricLevel` for banded descriptors. Add `RubricScore` (feedback FK, criterion FK, pointsAwarded, comment) and derive `Feedback.grade` as the sum instead of typing it — keep the existing integer column as the computed total so LecturerController.exportMarks and every existing query keep working unchanged. In review-split.html replace the single grade input with a criterion list (each row: descriptor + points input + optional per-criterion note), keeping the free-text box as an 'overall comment'. Critically, copy Gradescope's retroactive behaviour: editing a criterion's maxPoints or a shared deduction recomputes every RubricScore already recorded for that assignment — a single UPDATE plus a recompute of the parent Feedback totals. Render the same rubric read-only on student/new-submission.html *before* upload and on student/submission-detail.html after grading, so the marking scheme is the brief.
- **why** A bare number is the least actionable feedback possible, and it is the form most student-built apps stop at. Rubrics simultaneously fix three problems the roadmap treats separately: grader consistency, student clarity about what feedback means, and appeal-ability. It also unlocks per-criterion analytics for free (which criterion did the cohort fail?).

### No anchored feedback — comments float beside the document instead of pointing at the sentence they are about
- **severity** medium · **effort** L · **category** inline-annotation
- **evidence** https://community.canvaslms.com/t5/Instructor-Guide/How-do-I-add-annotated-comments-in-student-submissions-using/ta-p/694 ; https://docs.github.com/en/education/manage-coursework-with-github-classroom/teach-with-github-classroom/leave-feedback-with-pull-requests ; https://td.usnh.edu/TDClient/60/Portal/KB/ArticleDet?ID=1392
- **detail** Feedback attaches to a whole `SubmissionVersion`. A lecturer writing 'your methodology section confuses validity and reliability' has no way to point at the paragraph. Canvas DocViewer lets graders drop point, highlight, strikeout, free-text and area annotations directly onto PDF/DOC/PPT submissions inside SpeedGrader. ### Similarity is built for collaborator discovery only — there is no originality view, and semantic vectors alone will accuse the innocent
- **severity** high · **effort** L · **category** originality-reporting
- **evidence** https://guides.turnitin.com/hc/en-us/articles/34400565079053-Turnitin-and-plagiarism ; https://guides.turnitin.com/hc/en-us/articles/23435833938701-Understanding-the-similarity-score ; https://guides.turnitin.com/hc/en-us/articles/23539146689549-How-exclusion-filters-refine-the-Similarity-Report ; https://guides.turnitin.com/hc/en-us/articles/28477544839821-Turnitin-s-AI-writing-detection-capabilities-FAQs ; https://www.buffalo.edu/lms/guides-instructors/integrations/turnitin.html
- **detail** `SubmissionSimilarity` already stores a composite score with a per-signal breakdown (keywordScore, titleScore, unitScore, matched technologies/research areas) — genuinely good infrastructure. But it is surfaced exclusively as `similarProjectsPanel` on student/submission-detail.html:88 in a 'find a collaborator' framing, and EvaluationService measures it against accepted collaboration requests as ground truth. There is no staff-facing integrity view anywhere.

Two things follow from how Turnitin does this. First, the framing: Turnitin is explicit that it does not check for plagiarism — it highlights matches for a human to review, a high score does not imply plagiarism and a low score does not imply its absence, and the report is not a replacement for instructor expertise. Second, the mechanics: usable reports depend on exclusion filters — quoted material, bibliography (detected automatically), and matches under N words — because without them every properly-cited paper looks guilty. Turnitin also treats student visibility as an instructor-controlled setting, and deliberately withholds the AI-writing indicator from students entirely.

The specific technical risk for UniSubmit: pgvector cosine similarity is a *topical* measure. Twenty students told to build a school fee management system in PHP will all score 0.9 against each other while sharing not one sentence. A semantic score presented as an originality signal is a false-accusation engine.
- **do** Split the concept in two rather than reusing one score. Keep the existing panel as 'Related work' for discovery. Add a separate staff-only Originality panel on lecturer/review-split.html driven by a *verbatim* layer: hash overlapping word-shingles (k≈8) of the Tika-extracted text into a `TextFingerprint` table, and report longest common passages with the matched text shown side by side — that is cheap, deterministic, needs no API key, and is what actually evidences copying. Report the two numbers separately and label them honestly: 'Topic overlap 91% (same subject area — expected)' vs 'Verbatim overlap 34% across 7 passages'. Add exclusion toggles for quoted text, everything after a Bibliography/References heading, and matches under N words, and recompute the percentage live. Put a fixed interpretive line under every report: matches are not proof of plagiarism and require review. Gate student visibility behind a per-assignment `showOriginalityToStudent` flag, defaulting off, and — since Kenyan universities almost always require it — make the self-check case explicit: let students see their own verbatim report on a DRAFT before the deadline so they can fix citation errors, which is the use that actually improves work.
- **why** An originality report is the feature that makes staff take a submission system seriously, and it is the feature a student-built app most often gets dangerously wrong by shipping a raw similarity percentage with no exclusions and no framing. Given the pgvector engine already installed, the risk is not that this is missing — it is that the existing score gets repurposed as an accusation.

### Determinate progress for bulk import and AI analysis - stop reloading the whole page

### Undo-after-the-fact instead of confirm-before - and promote toasts off phones
- **severity** medium · **effort** M · **category** error recovery / feedback

- **detail** Gmail's model is the canonical one: perform the action immediately, show a toast ('Conversation moved to Trash') with an Undo affordance for a few seconds, and let silence mean commit. One `UndoController`, one short-lived table (or session attribute, since it is single-school and short-lived). Because AuditLog already records STATUS_CHANGED with prior state, the snapshot for the highest-value case (review decision) is close to free.

One prerequisite fix: `.alert.toast-mode` in base.css (line ~2432) is gated to phones only. Undo affordances must be visible on desktop too - that is where lecturers do grading. Promote toast-mode to all viewports, and make the undo toast persist longer than the standard flash (do not auto-dismiss at 3s if it contains an action).

Where NOT to use it: account deletion and anything touching credentials should keep an explicit confirm. Undo is for the reversible middle ground.

### Inline row editing on the admin CRUD screens - kill the list-then-separate-form round trip
- **severity** medium · **effort** S · **category** inline editing
- **evidence** https://github.com/wimdeblauwe/htmx-spring-boot ; https://tucanoo.com/htmx-with-spring-boot-and-thymeleaf-a-production-grade-guide-beyond-the-to-do-app/ ; https://spring.io/blog/2024/03/15/hypermedia-and-browser-enhancement/ ; https://www.925studios.co/blog/linear-design-breakdown-saas-ui-2026
- **detail** This is the finding where I want to be most explicit about the SPA question, because it is the pattern most often assumed to need one. It does not.

ZERO-JS version (ship this): render a collapsed `<details>` inside each table row containing a pre-filled edit form that POSTs to the existing update endpoint and redirects back to `/admin/units#row-42`. The browser restores scroll to the anchor for free. No JS, no new dependency, works with the service worker, and the markup change is confined to one `th:each` block per screen. Cost: a few hours per screen, less if you extract a shared fragment. The tradeoff versus true inline editing is a page reload on save - acceptable, and vastly better than today.

TRUE inline version: htmx is the standard answer in the Spring/Thymeleaf world and is designed for exactly this - the controller returns a Thymeleaf *fragment* (`units :: row`) instead of a full page, and htmx swaps the row in place. wimdeblauwe/htmx-spring-boot provides `@HxRequest` and an `hx:` Thymeleaf dialect so a controller can serve both the full page and the fragment from one method. Two caveats before adopting: (1) it is ~14KB of new dependency against a minimal-JS principle and a 512MB container - defensible, but it is a real architectural commitment; (2) Spring Security CSRF will silently break htmx POST/PUT/DELETE unless the token is wired into `hx-headers` - budget for that, it is the standard first bug.

Recommendation: do the zero-JS `<details>` version now, and only reach for htmx if you later find yourself wanting fragment swaps in three or more places (the AI insight panel from the progress finding would be the second, the notification list the third - at which point htmx pays for itself and also cleans up initInsightPolling).
